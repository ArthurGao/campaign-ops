# 03 — Agents

Three agents, split by **what they can read, what they can touch, and how bad a mistake is** — not by channel. All are read-only and produce items a human reviews. Phase 1 simulates them; the interfaces are real.

```ts
interface AgentAdapter {
  id: 'audit' | 'outbound' | 'feedback';
  run(input: AgentInput, ctx: RunContext): Promise<AgentOutput[]>;   // Mock*: resolves after 2–6 s
}
```

`RunContext` provides read-only repositories. **The Outbound adapter is constructed with a `FactSheetReader` that only exposes the external page** (enforced by type: `ExternalFactReader`).

Prompts live in `packages/core/src/integrations/agents/prompts/*.md`, copied from the "Instruction" sections below, so the mock and a future real agent share the same contract.

---

## Audit agent (诊断)

**Job**: see what is actually there — website, tracking, channels, SEO, GEO baseline. Read-only. Produces evidence, never recommendations.

**Inputs** (form on the Agents page)
- `siteUrl` (string)
- `scope`: multi-select of `site | tracking | channels | seo | geo | sales`
- `geoQuestions` (array, default 5 seeded questions), `geoPlatforms` (default 2)
- optional `testEnquiryApproved` (boolean) — only then the mock includes the sales-response observation

**Outputs**: `evidence` items with proof labels, `observation` items for GEO (question, platform, mentioned?, accurate?, cited sources), each tagged `source`.

**Mock behaviour**: returns the 8 seeded evidence candidates filtered by `scope`, plus `5 × 2 × 2 = 20` GEO observations summarised into 5 `observation` outputs (one per question) when `geo` is in scope. Marks ownership questions it cannot answer as "ask client" rather than guessing. Fails if `siteUrl` is empty (simulated `failed` run with error "No URL provided").

**Instruction (prompt)**
```
Role: Audit agent for the China Tour 2027 project. You look at public pages and client-authorised read-only data. You never change anything and never contact third parties.
You receive: site URL, scope, fixed GEO questions and platforms, optional permission for one TEST enquiry.
You return: evidence items only — finding, proof (URL/screenshot label/request log), impact, what it blocks, suggested owner, needs approval. For GEO: per question per platform — mentioned or not, accurate or not, sources cited.
Rules: attach proof to every finding; mark uncertain items "unconfirmed"; mark ownership (whose Pixel/GTM) as "ask client"; report problems, do not propose solutions.
```

## Outbound agent (出稿)

**Job**: everything that goes out, before it goes out — drafts, fact checks, publish-package assembly, post-publish verification.

**Inputs**
- `mode`: `draft | qa | verify`
- `taskId`
- for `draft`: `channel`, `spec` (e.g. "≤80 words, must include departure date, link at end"), `factSheetVersion`
- for `qa`: `briefId` (receipt available) or task body
- for `verify`: `packageId`, `livePostUrl` (mock)

Context given automatically: **external Fact Sheet entries only**, brand rules, channel specs, prohibited words, UTM link (generated by template — the agent cannot alter it).

**Outputs**
- `draft`: body with every fact followed by its FS id, `factRefs`
- `needs_confirmation`: when the spec requires information whose FS entry is not publicly usable — body explains which FS id and why; **no draft text is produced for that part**
- `evidence` (from QA): spec mismatches, facts outside allowed list, prohibited words found
- `verification`: diff between live content and approved version (`match` or list of differences)

**Mock behaviour**
- `draft` with spec containing "departure date" while `FS-04` is not usable → single `needs_confirmation` output (demo flow F1). Otherwise returns a placeholder draft like `[Itinerary highlight ← FS-07] … [Inclusions ← FS-11] … Learn more: {link}` with `factRefs = ['FS-07','FS-11']`.
- `qa` on the seeded delivered brief → passes ratios/checksums, flags nothing; on a brief whose receipt `factsUsed` includes an id outside `allowedFacts` → `evidence` "facts_used outside allowed_facts".
- `verify` → `match` for seeded `published` package, `mismatch` (caption differs by one sentence) for the seeded `mismatch` package.
- Prohibited word check: if the task body contains any `settings.prohibitedWords` → `evidence` output.

**Instruction (prompt)**
```
Role: Outbound agent for the China Tour 2027 project. Everything public passes through you before it is published.
You receive: a task card (ID, type, channel), the Fact Sheet EXTERNAL page with version, brand rules, channel specs; for QA tasks also the factory receipt and brief; for verification the live content and the approved version.
Do one of: (a) Draft — write per channel spec, put the FS id after every fact; (b) QA — check ratio/length/checksum against the brief and that facts_used ⊆ allowed_facts; (c) Verify — list differences between live and approved.
Rules: cite only entries marked confirmed on the external page; if the spec needs price, dates, seats or visa information that is not confirmed, output needs_confirmation naming the FS id and stop — never fill it in; do not edit UTM links; do not publish, schedule or send briefs; use only material provided in this task.
Return: task ID, status (draft_done | qa_passed | qa_returned | needs_confirmation | mismatch), content or issue list, FS ids used, Fact Sheet version.
```

## Feedback agent (回流)

**Job**: what came back — spend, traffic, leads, reconciliation, anomalies, suggestions. Runs **twice a week** plus one extra run after major launches/changes; it does not run daily.

**Inputs**
- `dateRange` (default last 10 days)
- `scope`: `ads | funnel | reconciliation | leads_quality`
- optional `afterLaunchOf` (task/package id) → trigger `after_launch`

Context: ad platform reports (mock), GA4 (mock), **de-identified** CRM export, publish/change logs, internal Fact Sheet page (targets, close rate) — the only agent allowed to see the internal page.

**Outputs**
- `observation`: funnel by layer, over-report ratio per channel, paid CPL per channel or "no valid leads yet, spent X"
- `suggestion`: proposed change with evidence, `inScope` (within pre-approved scope?) and who must approve; stop-loss hits are labelled `immediate`
- `evidence`: anomalies (Lead events dropped to zero, spend jump, landing page errors reported by the daily owner)
- `verification`: after an accepted ad change, confirms platform state matches the change record (mock)

**Mock behaviour**
- Default run returns: 1 funnel observation, 1 reconciliation observation (including one channel with zero valid leads and non-zero spend), 1 suggestion "Pause Meta ad set B" (`inScope: true`, evidence: spend reached threshold, 0 valid leads, 3 leads marked invalid "wants independent travel"), 1 anomaly if `settings.landingPage.status === 'not_ready'`.
- `leads_quality` scope: groups invalid leads by reason and by `adDetail` (campaign/ad/utm_term/landing page version); rows with `resolution = 'unknown'` are listed as "unknown — not inferred".
- `after_launch` trigger returns one `verification` output.

**Instruction (prompt)**
```
Role: Feedback agent for the China Tour 2027 project. You read results; you never change ads, budgets or content.
You receive: ad platform exports, GA4 exports, de-identified CRM export (no names/emails/phones), publish and change logs, internal targets, date range, scope.
Return: observations by funnel layer (impressions → visits → valid leads → deposits), reconciliation per channel (platform-reported vs CRM valid leads, over-report ratio, paid CPL = channel spend ÷ de-duplicated valid leads attributed to the channel; if valid leads are zero, report "no valid leads yet, spent X"), anomalies with evidence, and suggestions — each with evidence, whether it is inside the pre-approved scope, and who must approve.
Rules: CRM is the only ledger; platform numbers are for diagnosis only; treat two weeks as a checkpoint, not proof — state when the sample is too small; group invalid leads by stated reason and by campaign/ad/keyword/landing-page version, and mark unknown attribution as unknown rather than inferring; never recommend actions outside the scope without flagging them.
```

## Run lifecycle (all agents)

1. `POST /agents/:id/runs` → `queued` (returns run id immediately)
2. Service timer: `queued → running` after 500 ms; `running → completed|failed` after 2–6 s (seeded per agent for a stable demo)
3. Outputs appear on completion; cost estimate is a mock `{ tokens, usd }`
4. Each output is reviewed: `POST /agents/runs/:runId/outputs/:outputId/decision` with `accepted|rejected` + note → creates linked record per I-A1/I-A2
5. UI polls `GET /agents/runs/:id` every 2 s while `queued|running`

Guardrail text shown under every agent card: **"Read-only. Produces drafts and suggestions only. A person accepts each item."**
